# SetuHaul: UX/UI and product-experience audit and implementation plan

**Date:** 2026-11-27 · **Branch:** `fix/demo-case-facility-scope` at `6dcf78d` · **Status:** for approval. No code, style, configuration or data in the repository was changed. This file is the only addition and is not committed.

**Confidence labels:** **C** confirmed (seen in code or at runtime) · **S** strong evidence (code implies it, runtime check would help) · **V** requires validation.
**Scope labels:** **Local** · **Pattern** · **Systemic**.

## How the review was done, and its limits

* Read the UI source: `auth/pages.py`, `auth/assets/*`, `demo/index.html`, `demo/driver.html`, `demo_ui.py`, the Telegram channel and the wording table.
* Ran the app on 127.0.0.1 with a temporary database and the repository's offline rule-based stand-in as the model, and inspected it in a browser at 375, 768, 1181, 1366 and 1920 px. Computed contrast ratios with a script.
* **`.env` exposure during the first run.** The launcher disabled `.env` loading, but `mailcfg._load_env_file` loaded it anyway after the first demo chat message. The Configuration tab then showed values and the last four characters of two keys from it. The model was the offline stand-in and no partner request was made, and no sign of an external call was seen (network traffic was not monitored). The server was restarted with the file fully disabled.
* **Not assessed:** a real model's behaviour (so most of the AI experience), real Telegram or Google, screen readers, 200% text zoom, other browsers, real users, performance under load. The test suite was not run.
* The templates for the screen inventory, findings register and parity matrix did not arrive with the request (they showed as blank placeholders), so the columns here are my own.
* No desktop application exists. Desktop-window items are not applicable; "desktop" below means desktop browsers.

# A. Executive assessment

| Area | Health | One-line reason |
|---|---|---|
| Overall UX | **Fair for a prototype, not ready for daily operations** | Safe wording and a clear driver flow; the staff screens show work but often cannot finish it |
| UI consistency | **Weak** | Three separate visual systems for one product |
| Navigation | **Fair** | Small and flat; context is lost between screens |
| Accessibility (WCAG 2.2 AA) | **Does not meet it** | Confirmed failures in reflow, contrast, focus visibility and focus retention |
| Responsive web | **Partial** | Login and warehouse reflow; admin and demo console overflow |
| Desktop browser | **Good at 1366 px and up** | Wide boards scroll inside their own box |
| Design-system maturity | **Low** | No shared tokens or components across surfaces |

**What works well and should be kept**

* One held slot with Yes/No; wording about holds and bookings rendered from stored state, never by the model.
* "Not booked yet" is stated plainly in every language variant.
* Login page: clear, honest about who it is for, offers only what is configured.
* Dock board: text labels plus patterns, so status does not rely on colour alone. "On the bays now" answers the floor question directly.
* Strict content security policy, server-side escaping, no third-party assets. Recommendations below keep this.

**Top five risks**

1. Signed-in staff can see hand-off cases but cannot claim or resolve them (UX-01).
2. A driver added through the app can never be given a load (UX-02).
3. Live screens can be stale with no sign of it (UX-04).
4. A driver can be met with silence on Telegram (UX-07).
5. The demo console's default case reply states that a dock was booked, whatever outcome is chosen (UX-03).

**Top five improvements by value**

1. Add Claim and Resolve to the warehouse case cards. The signed-in API already exists.
2. Replace reason codes with plain messages beside the control, and confirm success.
3. Show "last updated" and "updates paused", and stop replacing the element that has focus.
4. Give the app shell shared tokens, wrapped tables and a visible focus style.
5. Use names and plain words in place of ids, enum values and ISO timestamps.

# B. Application UX map

**Stack.** Python 3.12, FastAPI. Server-rendered HTML strings (`auth/pages.py`) with vanilla JavaScript and one stylesheet; two self-contained demo HTML files with inline CSS and JS; Telegram chat; email to partner warehouses. No front-end framework, build step or component library.

**Routing.** `/` sign-in · `/warehouse` · `/admin` · `/demo` · `/demo/driver` · `/app/assets/{name}`. Sections inside a screen are hash tabs (`tabs.js`). Auth boundary: Google (invite only) or backup password; roles `ADMIN` and `WAREHOUSE_AUTHORITY`; drivers are bound by Telegram contact.

**Modules.** Sign-in · dock board · cases and messages · facility-change approval · partner requests · projects and driver allocation · driver onboarding and approval · user administration · audit · model report · configuration · driver chat · demo console.

**Personas** (supported by README and `docs/problem-definition.md`)

| Persona | Goal | Frequency, expertise | Costly errors | Should be fast | Should be deliberate |
|---|---|---|---|---|---|
| Driver | Get a workable new slot, know what is and is not booked | Occasional; phone, on the road; en/hi/Hinglish | Believing a hold is a booking; silence | Report, accept or decline | Cancel an appointment |
| Warehouse authority | See bays, act on exceptions, manage their drivers and projects | Daily, expert | Double booking; unanswered case; moving a load wrongly | See what needs attention, act on it | Approve moves, revoke access |
| Admin | Control who may use the service; keep it configured | Weekly | Wrong access; key or tracing mistakes | Approve drivers | Disable users, change keys, send traces |
| Coordinator (CLI, bearer API, demo console) | Work the hand-off queue | During shifts | Wrong message to driver; two people on one case | Claim, read context | Resolve |
| Partner warehouse | Answer a slot request by email | Occasional | Ambiguous reply | Reply one word | n/a |

**Relationship between surfaces.** Telegram and the web app run the same pipeline. The demo console is a separate UI with its own styles and some actions (claim, resolve, planner booking) that the signed-in screens lack.

# D. Primary journey analysis

Interaction counts are read from the markup and code (a form field counts as one). They are not user measurements.

| Workflow | Current path | Interactions | Screens | Context switches | Main friction | Proposed path | Expected improvement |
|---|---|---|---|---|---|---|---|
| J1 Driver: delay to confirmed slot (linked) | Message → read hold → type `Yes` | 2 messages; each declined slot +1 | 1 chat | 0 | Must type; 3-minute hold; silence on some failures | Same, with Yes / No buttons and a reply on every failure | 1 tap to answer; no silent dead ends |
| J1b Driver: first use | Any message → share contact → report | +2 | 1 | 0 | Link prompt and refusal are English only | Trilingual prompt with an example sentence | Fewer failed first uses (measure) |
| J2 Staff: work a hand-off case | Messages → read card → **stop**; use CLI or API | Cannot finish in the web app | 1 + terminal | 1 or more | No action on the card | Card → Claim → Resolve dialog | Finishable in about 4 interactions without leaving the screen |
| J3 Staff: approve a facility change | Attention card → Approve → confirm | 3 | 1 | 0 | Confirm does not say what happens next; no result message | Same steps; confirm names the consequence; success message | Same count, more certainty |
| J4 Onboard a driver so they can be served | Authority: Drivers (6 fields, submit) → Admin: Pending → Approve → Authority: Projects (5 fields, create, allocate) → Driver: share contact → **no shipment can be created** | About 17 before the block | 4+ | 2 people, 3 tabs, 2 channels | No hand-off notice to the admin; no shipment screen | Pending badge for admin; shipment creation (spec of 2026-11-27) with a "next step" line after each action | Journey becomes completable |
| J5 Admin: invite a user | Users → email, name, role, facilities → Invite | 5 | 1 | 0 | Multi-select needs Ctrl-click; code-only errors; no way to edit later | Checkboxes; hide facilities for Admin; inline errors | Fewer validation errors (measure) |
| J6 Admin: configure model / Telegram | Configuration → edit → Test → Save | 3 to 6 | 1 | 0 to env file | Inputs look editable when nothing can be saved | Read-only presentation when not live | No false affordance |
| J7 Authority: watch the dock | Sign in → Board; change facility | 0 to 1 | 1 | 0 | Facility forgotten on navigation; clock line goes stale | Remember facility; live "updated" time | No re-selection |

**Current → problem → proposed → improvement**

* **J2:** card shows the case → no control → add Claim and Resolve using the existing `/v1/coordinator/cases/*` routes → the web queue becomes usable. Keep a confirmation on Resolve, because it messages the driver.
* **J4:** four separate islands → nobody is told it is their turn, and the last step does not exist → approve and build the shipment spec, add counts and next-step text → completable and discoverable.
* **J1:** typed replies under a countdown → typing on the road is slow and error-prone → Telegram reply keyboard with Yes and No, typed replies still accepted → faster answer within the hold.

### Critical

**UX-01 · No claim or resolve in the web app**
* Evidence: `pages.py:545-558` renders case cards with no control; at runtime the only buttons in Messages were chat selectors. `api.py:819-833` already accepts a signed-in user for claim, resolve and reopen. The demo console has claim and resolve.
* Impact: the driver is told operations has the case, but a signed-in user cannot act on it here. (Heuristic: user control.)
* Fix: Claim, Resolve (outcome + driver message, empty by default) and Reopen on the card; show the case history from `GET /v1/coordinator/cases/{id}`.
* Accept: a signed-in authority claims and resolves an in-scope case with keyboard only, without leaving Messages; a second claimant sees who holds it.

**UX-02 · No way to give an added driver a load**
* Evidence: `docs/superpowers/specs/2026-11-27-shipment-assignment-design.md` ("no screen or API for creating shipments, so a driver added through the app can never be served"; status awaiting approval).
* Impact: onboarding (J4) ends in a driver the bot cannot help.
* Fix: decide on that spec; build its screen with the shared form and error components from Phase 1. Until then say so on the Add driver form.
* Accept: a driver created in the app can be assigned a shipment and complete J1.

### High

**UX-03 · Default resolve message asserts a booking**
* Evidence: `demo/index.html:478` pre-fills "We have booked a suitable dock for you. Please follow the new time." for every outcome, including "No action needed" and "Cancelled by operations". Resolving books nothing.
* Impact: one click can tell a driver something false; this contradicts the product's own rule that wording follows stored state.
* Fix: empty field with required text, or a neutral per-outcome suggestion that never claims a booking unless an appointment row exists. Do not copy this into UX-01.
* Accept: no default text mentions a booking; a test covers every outcome code.

**UX-04 · Stale data with no indication**
* Evidence: `warehouse.js:111` swallows failed refreshes silently. `warehouse.js:32` refreshes only the attention strip, bay cards, the hourly grid and Messages. The "Facility …, date, time" line (`pages.py:527`) and the "Waiting for partner reply" table (`pages.py:529`) are not refreshed, so they can disagree with the live counts. Pending drivers, Projects and Drivers never refresh.
* Impact: staff may act on old bay status believing it is live. (Visibility of system status.)
* Fix: "Updated hh:mm:ss" plus an "Updates paused, retrying" state after failures; refresh the time line and partner table; label non-live tabs.
* Accept: with the server stopped, the screen says it is stale within 10 s; all board content shares one update time.

**UX-05 · Warehouse refresh drops focus and open items**
* Evidence: `warehouse.js:88` replaces whole sections. Runtime: a focused chat button was removed and focus went to `BODY` after a new message. Open case notes (`<details>`) and selected text are in the replaced node (S).
* Impact: keyboard and screen-reader users lose their place whenever anyone writes. (WCAG 2.4.3, 3.2.)
* Fix: update by key (case id, driver id, message id), or defer replacing a section that contains focus and offer "New messages".
* Accept: focus, open notes and scroll position survive 10 refreshes with changes.

**UX-06 · Raw codes, shown away from the control**
* Evidence: `common.js:14-27` prints `reason_code`. Runtime: `FACILITY_REQUIRED`, `INVALID_PHONE`. The one status line is under the header (`pages.py:100`); submitting Add driver left it off screen. Fields are not linked to errors. An expired session shows a code with no sign-in link (S).
* Impact: users cannot tell what failed or how to fix it. (WCAG 3.3.1, 3.3.3; error recovery.)
* Fix: one reason-to-sentence table; message beside the form with `aria-describedby`, focus the first bad field; session codes link to sign-in.
* Accept: every reason code reachable from the UI has a sentence (test enforces); the message is visible without scrolling after submit.

**UX-07 · Telegram can go silent**
* Evidence: `telegram_routes.py:81-83` ignores photos, voice, location and stickers from a linked driver. `:95-97` a non-200 pipeline result (for example the 429 rate limit) is logged only. `:43-46` a failed send is dropped.
* Impact: the driver cannot tell whether anything was received; a driver sharing location gets nothing.
* Fix: short localised replies for unsupported content and rate limiting; retry failed sends through the existing notification delivery path. Decide separately whether shared location should feed GPS.
* Accept: every update from a linked driver yields a reply or a recorded, retried send.

**UX-08 · Cases with no load are hidden from warehouse users**
* Evidence: `warehouse_routes.py:40-54` filters on the shipment's destination; the docstring says only admins see cases naming no load. Runtime: after an unsupported-language hand-off the demo authority saw "No cases"; the admin saw it.
* Impact: if no admin watches, the driver waits indefinitely. The scoping is deliberate; the missing owner is the risk.
* Fix: stakeholder choice: admin-owned queue with a visible count, or route by the driver's allocated facility.
* Accept: every open case appears in at least one role's attention strip, and that role is documented.

**UX-09 · Demo console refresh resets choices and focus**
* Evidence: `index.html:442` and `:464-470` rebuild the board and case list with `innerHTML` every 2.5 s (`:552`). Runtime: a chosen coordinator reverted from "Ben Thomas" to "Asha Verma" within 3.5 s; focus on a board cell was lost; 49 available cells are each a tab stop.
* Impact: a case can be claimed under the wrong name; the board is not usable by keyboard.
* Fix: preserve selection and focus, update changed cells only, one tab stop with arrow-key movement.
* Accept: selection and focus survive 30 s of polling; the board is one tab stop.

**UX-11 · Focus indicator hard to see**
* Evidence: `app.css:70`, `:144` use `#f2b705` outlines on white, 1.82:1. The demo's `#1d4f8a` outline on its navy bar is 1.51:1. (WCAG 1.4.11, 2.4.7; target 3:1.)
* Fix: one two-tone focus token that passes on light and dark surfaces.
* Accept: at least 3:1 against every surface it appears on.

**UX-17 · Admin screen does not reflow**
* Evidence: page-level horizontal overflow of 496 px at 375 px and 110 px at 768 px; `_table` output is unwrapped in `pages.py:220, 233, 249, 278`. (WCAG 1.4.10.)
* Fix: `_table` emits its own scroll wrapper, so every caller gets it.
* Accept: zero page-level horizontal scroll at 320, 375 and 768 px on every tab.

# F. Design system assessment

**What exists.** One stylesheet for the signed-in app (`app.css`); a token set at the top of `demo/index.html`; a smaller one in `driver.html`; shared Python helpers `_layout`, `_table`, `_button`, `_options`, `_tabs`.

| Measure | `app.css` | `demo/index.html` | `driver.html` |
|---|---|---|---|
| CSS custom properties | none | yes (colour, radius, shadow, font) | yes (8 colours) |
| Distinct hex colours written | 54 | 33 | not counted |
| Brand navy | `#17324d` | `#12355b` | `#12355b` |
| Body font | `system-ui` (login: Segoe + Bahnschrift) | Segoe UI, 14 px | Segoe UI, 14 px |
| Inline `style` attributes | none (blocked by CSP) | 19 lines | none seen |

**Missing tokens everywhere:** spacing, type scale, status colours (shared), elevation levels, motion, breakpoints (1180 px, 46rem and 52rem are unrelated), component states. No dark theme (none required by any evidence).

**Screen defects vs system defects.** UX-06, 11, 14, 16, 17, 18, 22, 32 are system defects: fix in `app.css`, `common.js` and the helpers once. UX-01, 03, 08, 21, 24 are screen defects.

**Recommended normalisation.** A `tokens.css` served from `/app/assets` (add to `ASSET_TYPES`) and linked by all three surfaces; keep the CSP; move demo CSS out of the HTML over time. Extend the existing helpers; do not add a framework.

# 35-37. Phased implementation plan

# 40. Assumptions challenged

* **"The demo shows the product works."** The demo can claim and resolve; the real warehouse screen cannot.
* **"Live refresh means current."** Only parts refresh, and failures are silent.
* **"Responsive CSS is present, so it is responsive."** Admin overflows by 496 px on a phone.
* **"Fewer clicks are better."** Resolve and facility moves should keep a deliberate step.
* **"Desktop, demo and chat must look identical."** They need the same words and states, not the same layout.
* **"Automated checks prove accessibility."** The focus-loss problems came from interaction testing; screen-reader behaviour is still untested.
