SetuHaul Rescheduling Service: architecture

A driver chat message goes in. The model interprets it. Deterministic code and the database decide, and the reply is built from committed rows.

What to take from it

  • The model never supplies identity. No tool takes a driver or thread id; identity comes from the verified phone or a server-made session.
  • The database is the referee. A hold is an appointments row with status HELD under the same unique index as a booking, so two drivers collide on a constraint, not in application code.
  • Facts come from committed rows. Hold, confirm, cancel and menu wording is rendered from stored state; unbacked model claims are replaced.
  • Redis is only a cache. Every message is committed to SQL first, and the memory window can be rebuilt from it.
  • Notifications are post-commit. The outbox row shares the booking transaction; delivery happens outside it.
